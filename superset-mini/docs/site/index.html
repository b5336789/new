Superset-mini

一個從零打造、擬真 Apache Superset 核心工作流程的 BI 應用：Python (FastAPI) 後端 + React (Vite) 前端，並在其上加入 Text → Chart（自然語言生成圖表）功能。

範圍誠實聲明 (Scope). 這不是 Apache Superset 的完整重製（其原始碼達數十萬行）。 它實作了完整的端到端核心迴圈 —— 連線 → 資料集 → 查詢 → 圖表 → 儀表板 —— 作為扎實、有測試覆蓋的基礎，並額外加上 text-to-chart。

架構 Architecture

後端擁有資料來源連線、查詢引擎與 metadata store；前端是 JSON API 之上的輕量客戶端。 刻意分離 metadata store（應用自身的物件）與 使用者資料來源（被分析的資料）， 這正是 Apache Superset 的做法。

┌─ Frontend (React + Vite) ─┐        ┌─ Backend (FastAPI) ───────────────┐
│ pages/  Databases          │  HTTP  │ routers/  /api/databases           │
│         Datasets + Upload  │ JSON   │           /api/datasets /api/sql   │
│         SQL Lab            │ ─────► │           /api/charts /api/dashboards
│         Explore (builder)  │        │           /api/upload  /api/nl     │
│         Text → Chart       │        │                                    │
│         Charts / Dashboards│        │ query_builder  QuerySpec → SQL     │
│ components/ ChartView      │        │ engine         connect/introspect  │
│   (Recharts)               │        │ services/text_to_chart  (Claude)   │
└────────────────────────────┘        └───────────────┬────────────────────┘
                                                       │ SQLAlchemy
                       ┌────────────────────────────────┼──────────────────┐
                       ▼                                ▼                  ▼
                 metadata.db                      examples.db          uploads.db
            (databases, datasets,              (seeded sample        (Excel/CSV
             charts, dashboards)                sales data)          imports)

分層 Layers

  1. Routers — HTTP 介面，Pydantic 驗證、錯誤對映到狀態碼，僅做協調。
  2. Query builder — 純函式，把 QuerySpec 轉成安全的參數化 SQL，無 I/O。
  3. Engine — 唯一與使用者資料來源溝通之處：連線池、schema 探查、執行 SQL。
  4. Metadata store — SQLAlchemy ORM，持久化於 metadata.db。
  5. Text-to-chart service — NL → QuerySpec（Claude），含確定性後備。

QuerySpec（內嵌於 Chart.params）

前端、查詢引擎、text-to-chart 三者之間的契約。

{
  "dimensions": ["region"],
  "metrics": [{"column": "sales", "aggregate": "SUM", "label": "total_sales"}],
  "filters": [{"column": "year", "op": "=", "value": 2023}],
  "order_by": [{"field": "total_sales", "desc": true}],
  "row_limit": 1000,
  "time_grain": "month",        // 選用：時間粒度
  "time_column": "order_date"   // 設了 time_grain 時必填
}

查詢引擎 Query Engine

引擎拆成純建構器（query_builder.py，無 I/O）與執行器 （engine.py，所有 I/O），讓建構器可被單元測試。

安全模型 Safety

兩道信任邊界：

  • 識別字（欄/表名）：放進 SQL 前，先對資料集已知欄位清單驗證，再雙引號包裹。 未知欄位 → QueryBuildError → HTTP 400。這是抵禦欄名注入的主要防線。
  • 字面值（filter value）：絕不內插進 SQL 字串，一律以綁定參數 （:f0…）傳給 driver。

時間粒度 Time Grain（Superset 招牌功能）

建構器具方言感知：SQLite 用 strftime，PostgreSQL 用原生 date_trunc。

-- 每月銷售額 (SQLite)
SELECT strftime('%Y-%m', "order_date") AS "order_date",
       SUM("sales") AS "monthly_sales"
FROM "sales"
GROUP BY strftime('%Y-%m', "order_date")
LIMIT 1000

註：試算表載入的日期常是 ISO 字串（2023-01-15），SQLite 的 strftime 可直接運算，故上傳資料也能用時間粒度。

SQL Lab 防護

/api/sql/run 僅允許 SELECT/WITH 開頭的語句， 並包成 SELECT * FROM (<user sql>) LIMIT n；異動語句（DELETE/UPDATE/DROP）回 400。

Text → Chart

把「自然語言 + 資料集 schema」轉成可執行的 QuerySpec + 視覺化類型， 端點 POST /api/nl/chart。

prompt + dataset.columns
        ▼  generate_chart_spec()        ANTHROPIC_API_KEY?
        ├── 有 ─► Claude API (tool use) ─► spec, source="claude"
        └── 無 ─► 啟發式 parser         ─► spec, source="heuristic_fallback"
        ▼  build_query()  驗證欄位、產生 SQL
        ▼  engine.run_sql()  對真實資料執行
        ▼  { viz_type, params, explanation, source, result }

產生的 spec 一律先對真實資料驗證並執行才回傳。若模型杜撰欄位， build_query 會拋錯，端點回 HTTP 422 —— 絕不靜默回傳跑不動的圖表。

Claude 路徑（主要）

用 Anthropic Messages API 的 tool use 強制結構化輸出：單一工具 create_chart，其 input_schema 對映 QuerySpec， 並以 tool_choice 強制呼叫。Schema 已放進 prompt、事後再驗證， 故幻覺欄位會被攔下。

export ANTHROPIC_API_KEY=sk-ant-...
export ANTHROPIC_MODEL=claude-opus-4-8   # 選用

啟發式後備（無 key）

確定性關鍵字 parser，讓功能在無 key 時仍可展示。它把每個回應標記為 source: "heuristic_fallback"，絕不假裝是 LLM（fail-loud 原則）。 會推斷聚合（total→SUM、average→AVG…）、指標欄、時間意圖（over time→line + 粒度）、 維度與視覺化類型。

本展示環境未設定 ANTHROPIC_API_KEY，故預設走 heuristic fallback； /api/health 與 UI 會明確標示目前採用哪條路徑。

做法 Methodology

本專案在開發前先放置 CLAUDE.md（AI coding 規則），並全程遵循。重點做法：

1. 先思考、先釐清範圍 (Rule 1)

「完整版 Superset」範圍極大且語意模糊，因此先以結構化問題釐清技術棧 （Python+React 擬真）、功能範圍（連線/資料集、SQL、圖表、儀表板 + Excel 上傳）、 以及 text-to-chart 的 LLM 來源（Claude），再動工。

2. 里程碑檢查點 (Rule 10)

  1. Checkpoint 1 — 後端：models / 查詢引擎 / 全部 routers / 種子資料 + 測試。
  2. Checkpoint 2 — 前端：Vite SPA、各頁面、Recharts 視覺化。
  3. Checkpoint 3 — 進階功能：時間粒度、CSV 匯出、Charts 管理與編輯。
  4. Checkpoint 4 — 技術文件 + 文件網站（本頁）。

每個檢查點都提交 (commit) 並驗證後才前進。

3. 目標導向與業務邏輯測試 (Rule 4, 9)

13 個端到端測試驗證真實結果而非空覆蓋率：例如 SUM(sales) 分區後是 4 列且 正確排序、未知欄位被拒、SQL Lab 拒絕 DELETE、Excel 上傳後 A = 10 + 30 = 40 立即可查、時間粒度產出 ≤24 個 YYYY-MM 月份桶。

4. Fail Loud (Rule 12)

連線失敗、欄位非法、LLM 解析失敗都明確回報並對映到適當的 HTTP 狀態； 無 API key 時 text-to-chart 走後備但清楚標記，絕不掩蓋不確定性。

5. 純函式 / I/O 分離 (可測試性)

查詢建構器保持純函式（無 I/O），執行器是唯一 I/O 邊界，讓查詢邏輯易於單元測試、 易於替換資料庫方言。

如何執行 Run

後端

cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000   # /docs 有 Swagger

前端

cd frontend
npm install
npm run dev      # http://localhost:5173 （/api 代理至 :8000）

測試

cd backend && source .venv/bin/activate
python -m pytest -q     # 13 passed

首次啟動會植入 Sample Sales 資料集（2000 列），圖表立即可用。
